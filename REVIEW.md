# Code Review & Starter Defects

Here is the audit of the bugs found in the starter code, how to reproduce them, and how each one was fixed.

## Starter Defects Inventory

| # | Where | What was wrong | How to reproduce / symptom | How it was fixed |
|---|---|---|---|---|
| 1 | `epoch_ms_to_datetime` | Used `datetime.fromtimestamp(ms / 1000)` without specifying UTC, shifting timestamps on non-UTC machines. | Passing `1783312500000` on a local machine gave a datetime shifted by the local timezone offset. | Used `datetime.fromtimestamp(ms / 1000, tz=timezone.utc)`. |
| 2 | `datetime_to_epoch_ms` | Converted naive datetimes to timestamps without ensuring UTC, which defaults to local machine time. | Naive datetimes returned incorrect millisecond counts on machines running outside UTC. | Normalized datetimes to UTC before converting to epoch milliseconds. |
| 3 | Input validation | Accepted floats, booleans, strings, and seconds-like numbers for timestamp fields. | Sending `{"punched_at": 1783312500000.5}` or `{"punched_at": true}` was accepted instead of returning 422. | Built a strict validator that rejects booleans and non-integers, and enforces bounds `[100000000000, 4102444800000]`. |
| 4 | Instant truncation (R1) | Kept fractional milliseconds during calculations, violating the rule that instants must be truncated to whole seconds. | Punches with fractional milliseconds produced inaccurate work hours and overtime calculations. | Floor-truncated epoch milliseconds to whole thousands (`ms - (ms % 1000)`) before saving or calculating. |
| 5 | `is_overnight_shift` | Checked `shift_end < shift_start` instead of `<=`, missing shifts where start and end times are identical. | Overnight boundary shifts were not detected properly. | Changed the check to `shift_end <= shift_start` as required by rule R1. |
| 6 | `derive_attendance_date` (R1) | Derived attendance date only from the punch-in calendar day, ignoring overnight shift rollover. | On a 22:00-06:00 overnight shift, punching in at 01:00 AM on July 7 was marked for July 7 instead of July 6. | Subtracted 1 day from the attendance date if the shift is overnight and punch-in time is before shift end. |
| 7 | `compute_late_minutes` (R2) | Counted an exact 10-minute delay as late (`>=` instead of `>`), and deducted the grace period from the late total. | Punching in at 09:40:00 (for 09:30 shift) was flagged as late; punching in at 09:40:01 gave 0 late minutes instead of 10. | Checked strictly `> 600` seconds late, then calculated whole minutes from `shift_start` without deducting grace. |
| 8 | `compute_overtime` (R3) | Counted overtime under 30 minutes and did not floor to whole minutes. | Punching out 15 minutes after shift end returned 15 overtime minutes instead of 0. | Added the 30-minute minimum threshold (`>= 1800` seconds) and floored to whole minutes. |
| 9 | `compute_work_hours` (R4) | Used Python's built-in `round()`, which uses Banker's rounding (round half to even) instead of half-up. | Durations ending in `.xx5` rounded down to even numbers instead of rounding up. | Used Python's `Decimal` with `ROUND_HALF_UP` to two decimal places. |
| 10 | `compute_half_day` (R5) | Did not compute `half_day` based on work hours, and missing fields were unhandled. | A punch-out with 3.5 hours worked did not set `half_day: true`. | Added logic setting `half_day = True` whenever rounded `work_hours < 4.50`. |
| 11 | `GET /health` | Returned a hardcoded `{"status": "ok"}` without checking if MongoDB was actually reachable. | Stopping the MongoDB service still returned 200 OK. | Added `client.admin.command('ping')` and returned HTTP 503 if the database fails to respond. |
| 12 | Database initialization | Did not create any indexes at startup, leading to full collection scans and duplicate records. | Queries on 100k records performed slow `COLLSCAN`s, and duplicate employees could be created. | Created `init_indexes()` on startup to build all required unique and compound indexes idempotently. |
| 13 | `POST /employees` duplicate race | Checked for `emp_code` using `find_one` before inserting, leaving a window for race conditions. | Sending two simultaneous create requests for the same `emp_code` created duplicates or crashed with 500. | Added a unique index on `employees.emp_code`, caught `DuplicateKeyError`, and returned HTTP 409. |
| 14 | `POST /employees` response | Returned the raw MongoDB document directly, exposing the internal `_id` field. | Response JSON contained `"_id": "6ad..."`, which violates the OpenAPI contract. | Built a serializer that strips `_id` and formats `created_at` as epoch milliseconds. |
| 15 | `GET /employees` pagination | Did not use `.skip()` for pagination, did not sort by `emp_code`, and `total` didn't reflect filters. | Requesting `page=2&page_size=10` still returned the first 10 records, unsorted. | Applied `.sort([("emp_code", 1)]).skip(skip).limit(page_size)` and used filtered `count_documents()`. |
| 16 | `POST /attendance/punch-in` duplicate race | Checked for existing records in Python before inserting, allowing concurrent punch-ins for the same date. | Two simultaneous punch-ins for the same employee and date both succeeded. | Created a unique compound index on `attendance_logs(emp_code, date)` and caught `DuplicateKeyError` as 409. |
| 17 | `POST /attendance/punch-in` status validation | Accepted `ABSENT` and `LEAVE` in punch-in request bodies. | Sending `{"emp_code": "EMP0001", "status": "LEAVE"}` succeeded with 201. | Restricted punch-in status to `PRESENT`, `WFH`, and `ON_DUTY`; rejected others with 422. |
| 18 | `GET /attendance` in-memory filtering | Fetched all attendance documents into Python memory before slicing, and missed date range validation. | Crashed with out-of-memory on 100k records; `date_from > date_to` returned 200 instead of 422. | Validated date boundaries (returning 422 if inverted) and pushed pagination/sorting down to MongoDB. |
| 19 | `POST /attendance/punch-out` race condition | Read the open record and then updated it without checking if it was still open. | Concurrent punch-outs with different times overwrote each other and both returned 200. | Used atomic `find_one_and_update({"punch_out": None}, ...)` so only the first request can close the record. |
| 20 | `POST /attendance/punch-out` overnight matching | Looked for punch-ins only on the current calendar day, failing for overnight shifts. | Punching out at 06:30 AM for a 10:00 PM overnight shift couldn't find the open punch-in from yesterday. | Selected the most recent open record where `punch_in <= punch_out`, sorting by `punch_in` descending. |
| 21 | `PATCH /attendance/{emp_code}/{date}` concurrency | Replaced the document unconditionally, so concurrent edits lost history entries. | Two simultaneous edits on the same attendance log resulted in one edit's history being lost. | Used optimistic concurrency matching the current history length on update, retrying if a collision occurs. |
| 22 | `PATCH /attendance/{emp_code}/{date}` no-op | Accepted regularization requests that didn't change any values and still appended an empty audit entry. | Sending `{"status": "PRESENT"}` when status was already `PRESENT` returned 200 and added a blank history log. | Compared existing vs incoming values; if no actual changes occurred, rejected with 422. |

---

## Examined Behaviors That Were Not Defects

1. **Storing UTC Instants alongside IST Dates**: MongoDB stores `punch_in` and `punch_out` as UTC BSON datetimes, while storing `date` as an IST date string (`"YYYY-MM-DD"`). This looks mismatched at first glance, but it is intentional: punch times are exact global instants, while attendance days belong to local Indian Standard Time (IST) per rule R1.
2. **Reading Stored Derived Fields in Analytics**: The analytics endpoints read stored `work_hours`, `late_minutes`, and `overtime_minutes` instead of recalculating them from raw punch times. This is correct per specification: stored values are authoritative and reflect manual regularizations.
3. **No Database IDs in the API**: The API never exposes MongoDB's `_id` and does not assign custom IDs to attendance logs. Instead, records are identified by natural keys (`emp_code` for employees, and `(emp_code, date)` for attendance).
